# Private · Claude Code Projects setup

## Owner setup

1. Open Projects in [Claude Code](https://claude.ai/code) on web or desktop. Check account availability in the current Projects documentation. The redesigned Projects coordinator is a beta feature with plan and rollout constraints. If unavailable, use one regular Claude Code cloud session as the coordinator and separate cloud sessions only for independent lanes. Track the same checkpoint and PRs manually.
2. Select or create a GitHub.com repo with owner-approved visibility and slug. While naming is unresolved, use a private repo or another access-controlled location for staging. Seed from `public-repo/` only. Protect the default branch with the checks and reviews available for the repo plan. Install the Claude GitHub App only on the selected repo. The connected user needs push access. Project threads require the app on repositories they clone even if standalone sessions use `/web-setup`.
3. Create a Claude Code Project and add the selected repo. Keep its visibility private where applicable. Use the [coordinator rules](COORDINATOR.md) as project instructions. Add the decisions, naming check, work plan and initial checkpoint to the private Project Library, or supply the relevant excerpts from approved private storage. Paste the kickoff in the coordinator conversation. Check that a worker can access the files it needs. Never place private docs or conversation exports in the code repo.
4. Select a trusted cloud environment. Use the same pinned runtime as CI once chosen. Keep setup repeatable and limited to approved package/browser registries. After baseline merge, use an idempotent setup step that installs the locked marketing dependencies from `apps/marketing`. Verify install and check commands in a fresh session. Browser test dependencies may run in GitHub Actions if unavailable in the cloud VM. Phase 0 needs no production credentials, database, connectors or broad network access. Keep automatic PR remediation disabled unless intentionally enabled.
5. Confirm that a worker can clone the repo and push its own branch or open a draft PR. Confirm CI can read the repository. Check that a PR cannot release. Set GitHub Pages source to GitHub Actions when ready, then protect the `github-pages` environment. If environment reviewers are unavailable on the plan, keep deploy disabled until the owner approves and use manual dispatch restricted to the default branch for the first release. Private-repo Pages entitlement and site access are separate. Use access-controlled CI artifacts until the intended public release, even if the repo itself is private.
6. Do a preflight on a clean baseline SHA. Record repo, base branch/SHA, active scope, publication gate, cloud environment, runtime version and eligible model tiers in the checkpoint. Review host changes before restarting after a long pause.

Prefer cloud environment settings for toolchain, network and secrets over assuming local settings or repo-level MCP and skill configuration is loaded. No private files or token values belong in PR descriptions, test logs, setup scripts, Actions artifacts or Pages.
