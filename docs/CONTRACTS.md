# Contracts and persistence (milestone 1.1)

Status: proposed defaults for owner review, per the roadmap. Nothing here is a product commitment. Decisions are recorded in [docs/adr/](adr/).

## Layout

| Path | Owner | Contents |
| --- | --- | --- |
| `apps/api/openapi/openapi.yaml` | contract | Versioned OpenAPI 3.1 skeleton, source of truth for HTTP shapes |
| `apps/api/migrations/` | persistence | Forward-only numbered SQL migrations |
| `apps/api/src/` | API | Identifier, shared types and migration runner (TypeScript); later milestones add modules |

## Local bring-up

```sh
docker compose -f deploy/compose.dev.yml up -d --wait
cd apps/api && npm ci
export DATABASE_URL=postgres://driveloom:driveloom-dev-only@127.0.0.1:54320/driveloom
npm run migrate      # empty database to latest
npm run check        # type-check plus OpenAPI validation
npm test             # set REQUIRE_DB=1 to fail rather than skip without a database
```

## Identifiers

All primary keys are UUIDv7 generated by the application (RFC 9562), stored as `uuid`. They are opaque, time-ordered and never reused. Clients must not parse them. Natural keys (email, OIDC issuer+subject, credential ids) are separate unique columns. Foreign keys use the same type.

## Migrations

Plain SQL files named `NNNN_description.sql`, contiguous from 0001, applied in order, each in one transaction, under an advisory lock so concurrent starters serialise. Applied files are recorded in `schema_migrations` with a SHA-256 checksum. Editing an applied file, a numbering gap, or a database containing a migration this build does not know is a hard error. Policy is forward-only: no down migrations. Recovery from a bad migration is restore from backup, which keeps data-destructive steps explicit. A migration that rewrites data must ship with a fixture in `tests/fixtures/` built from the previous snapshot. The current snapshot, `snapshot-0001.sql`, is the schema after migration 0001 and is used to test upgrade from a prior version.

Each migration is owned by the milestone that introduces its tables. Foreign keys to a table are added in that table's owner migration.

## Compatibility policy

- The API is versioned in the path (`/v1`). `info.version` in the OpenAPI document is semver.
- Within a major version: adding endpoints, optional request fields, response fields and enum values documented as extensible is minor. Removing or renaming a field, changing a type, tightening validation or changing authorization semantics is major and needs a new path version.
- Clients must ignore unknown response fields. Servers must reject unknown request fields only where the schema says `additionalProperties: false`.
- `GET /v1/version` reports server, API and schema versions so native clients can check support.
- Errors use RFC 9457 `application/problem+json` with a stable machine-readable `code`.
- A server upgrade runs migrations before serving. Downgrading to a build older than the database schema is refused.

## Decimal rules

- Decimals cross the API as strings matching `^-?(0|[1-9][0-9]*)(\.[0-9]+)?$`, never JSON numbers.
- In PostgreSQL use `numeric` with explicit precision, never `float`.
- Preserve the user's input quantity and unit. Store a normalised value in base units (litres, kilometres) alongside it. Convert at input boundaries and round only for display.
- Conversion constants: 1 US gallon = 3.785411784 L, 1 imperial gallon = 4.54609 L, 1 mile = 1.609344 km (exact by definition).
- Economy is computed from aggregated distance and volume, not by averaging per-fill ratios. Round half away from zero at display only.
- Currency amounts are stored as `numeric` with the ISO 4217 code; minor-unit rounding happens at display or when a reporting amount is derived.

## Test data

`apps/api/tests/fixtures/decimal-cases.json` holds shared cases: unit constants, the full-to-full example (500 km, 20 L partial plus 30 L closing is 10 L/100 km, starting fill excluded), an incomplete interval that must be unavailable, and unit round trips. Later milestones consume these and add fixtures beside them. Test databases are created per test and dropped afterwards. Tests never use shared or production data.

## Identity and authorization interface (milestone 1.2)

Status: proposed default, defined first so the vehicles lane (1.3) can build against it in parallel.

**What auth provides.** `apps/api/src/identity.ts` exports `Principal` (`userId`, `sessionId`, `instanceRole`, `authenticatedAt`), `RequestContext`, `requirePrincipal(ctx)`, `requireInstanceAdmin(ctx)` and `AuthError`. Route handlers receive a `RequestContext`; only the auth module creates a `Principal`. Anonymous routes declare `security: []` in OpenAPI; all others use the `session` security scheme and call `requirePrincipal` first.

**What auth does not decide.** Vehicle ownership, membership grants and every per-resource check belong to the vehicles lane. Auth proves who the caller is; vehicles decides what that user may do, server-side, on every read, mutation and export. `instanceRole = 'admin'` is for instance administration and audited recovery only and must not imply vehicle-data visibility. When a resource exists but the caller has no grant, respond 404 rather than 403 so existence is not leaked.

**Data contract.** Table `users(id uuid, email, display_name, instance_role, status, created_at)` is created by migration `0003_accounts.sql`. Other lanes may reference `users(id)` with a foreign key and must not write to `users` or any other auth table. Users are never hard-deleted by other lanes: account removal sets `status = 'deleted'` through the auth module, and a user who owns a vehicle must have ownership resolved by the vehicles lane's own policy first. Migration numbering: auth owns `0003`, vehicles starts at `0004`, merge order is auth migration first.

**Test helper.** `tests/helpers/` (added by auth) creates a user and a ready `RequestContext` without going through sign-in, so vehicles tests can act as separate actors.

**Errors.** `AuthError` codes: `unauthenticated` (401), `forbidden`, `csrf_failed`, `reauth_required` (403). The HTTP layer renders them as RFC 9457 problems with that `code`.

**HTTP layer.** `apps/api/src/http/app.ts` owns routing, JSON bodies (64 KiB default limit), cookie parsing, session resolution, the `Origin` and `X-CSRF-Token` checks for unsafe methods, trusted-proxy client IP resolution and problem+json rendering. A feature module exports `Route[]` (`method`, `path` such as `/v1/vehicles/:id`, `auth` mode, `handler`). The default `auth` mode is `required`, so a route is private unless it opts out, and handlers read `req.ctx` and call `requirePrincipal`. Handlers throw `HttpProblem(status, code, title)` for expected errors. Other lanes add their routes to the list passed to `createApp` and use `tests/helpers/` (`createTestDb`, `createTestUser`, `fakeAuthenticator`) for isolated databases and actors.

## Authentication (milestone 1.2)

Decisions and open questions are in [ADR 0002](adr/0002-authentication.md). The HTTP surface is the `auth` tag in `openapi.yaml` (`/v1/auth/...`), and `tests/auth-contract.test.ts` fails if routes and document drift apart.

**Operator configuration** (environment): `DRIVELOOM_PUBLIC_ORIGIN` (required, an origin such as `https://fuel.example.com`, fixed WebAuthn origin), `DRIVELOOM_SECRET_KEY` (at least 32 characters), `DRIVELOOM_RP_ID` (defaults to the origin host; keep stable once passkeys exist), `DRIVELOOM_REGISTRATION` (`open` or `closed`, default `closed`), `DRIVELOOM_SETUP_TOKEN` (optional, at least 16 characters; the first account must present it), `DRIVELOOM_PASSWORD_LOGIN` (`0` to disable), `DRIVELOOM_TRUSTED_PROXIES` (comma-separated IPs or CIDRs), `DRIVELOOM_SMTP_URL` and `DRIVELOOM_SMTP_FROM` (optional), `DRIVELOOM_REQUIRE_EMAIL_VERIFICATION=1` (needs SMTP), `DRIVELOOM_OIDC_ISSUER`, `DRIVELOOM_OIDC_CLIENT_ID`, `DRIVELOOM_OIDC_CLIENT_SECRET` (optional; the redirect URI is `<origin>/v1/auth/oidc/callback`). Start with `npm start` in `apps/api`.

**Auth tables** (all in migration 0003): `users`, `password_credentials`, `totp_credentials`, `recovery_codes`, `passkeys`, `oidc_identities`, `sessions`, `one_time_codes`, `auth_challenges`, `rate_limits`. Only the auth module writes them.

## Vehicles and ownership (milestone 1.3)

Code is in `apps/api/src/vehicles/`, schema in `0004_vehicles.sql`, HTTP shapes in the `vehicles` operations of the OpenAPI file. Authorization lives in `VehicleService`; `vehicleRoutes(service)` in `src/vehicles/routes.ts` exposes it as `Route[]` for the shared HTTP layer, and the application entry point (not yet written) passes those routes to `createApp`.

| Role | May |
| --- | --- |
| viewer | read the vehicle and its member roster, leave |
| editor | everything a viewer may, plus edit vehicle details (later: fuel records) |
| owner | everything, plus archive, grant, change or remove members, transfer ownership |

- **One owner per vehicle.** A partial unique index forbids a second owner. The service creates the owner row with the vehicle, never removes it, and swaps it only by transfer or recovery. Every mutation locks the vehicle row first, so concurrent transfers, removals and role changes serialise.
- **404, not 403, for strangers.** A caller with no grant, including an instance admin, gets `vehicle_not_found` on every operation. A member lacking permission gets 403 `forbidden`.
- **Transfer.** The owner hands ownership to an existing active member; the previous owner becomes an editor. The owner cannot be removed or have their role changed directly (`owner_required`, `owner_immutable`).
- **Admin recovery.** `recoverOwnership` is the only vehicle operation open to instance admins. It needs a written reason, makes an active user the owner, keeps the previous owner as editor (dropped if that account is disabled or deleted), and never grants the admin vehicle access.
- **Audit.** Each mutation writes an `audit_events` row in the same transaction: `vehicle.create|update|archive|unarchive`, `member.add|role_change|remove|leave`, `owner.transfer|recover`.
- **Account removal.** Auth must not delete a user who owns a vehicle until the owner transfers it or an admin recovers it.

- **Members by email.** `POST .../members` takes `userId` or `email`. An owner therefore learns whether an address has an active account on the instance; accepted because members are people the owner already knows and the instance is private. The roster shows each member's display name and email to the other members.
- **Admin listing.** `GET /v1/admin/users/{userId}/owned-vehicles` returns only ids and archive state, is admin-only (404 for others) and writes an `admin.list_owned_vehicles` audit row.

Owner decisions (2026-11-11): editors may edit vehicle details; the previous owner stays as editor after admin recovery; admins can list the vehicle ids a user owns.

## Fuel, units and costs (milestone 1.4)

Decisions are in [ADR 0003](adr/0003-fuel-units-costs.md). Code is in `apps/api/src/fuel/`, `src/decimal.ts`, `src/units.ts` and `src/preferences.ts`; schema in `0005_fuel.sql`; HTTP shapes under the `fuel` and `preferences` tags.

- **Entry.** A fill-up carries `occurredAt`, `odometer {value, unit}`, `volume {value, unit}`, `full`, `missedPrevious`, optional `cost` and `notes`. Units are always explicit. The entered value and unit are stored and returned unchanged; `odometer_km` (6 decimals) and `volume_l` (9 decimals) are the normalised values every calculation uses.
- **Order.** The authoritative order is `(occurred_at, odometer_km, id)`. The odometer may not run backwards in time: a reading must sit between its chronological neighbours (`odometer_out_of_sequence`, 422). Same vehicle, instant and reading is a duplicate (`duplicate_fill_up`, 409). Same instant with different readings is allowed.
- **Economy.** Full-to-full. An interval runs from one full fill to the next; the starting fill is excluded, partial purchases and the closing fill are included. It is unavailable, with a reason, when there is no earlier full fill, when a purchase in it is flagged `missedPrevious`, or when it covers no distance. A partial fill closes nothing. Aggregates sum distance and volume first.
- **No stored derivations.** Intervals and statistics are computed from the ordered records on every read, so a backdate, correction or deletion repairs its neighbours without a recalculation step.
- **Display.** Responses are in the caller's preferences (`/v1/preferences`: distance, volume, economy unit, currency). Odometer readings are shown in the vehicle's `odometerUnit`, the unit of the physical odometer. Display scales: distance 1, volume 2, economy 2 decimals, money in the currency's minor units, rounded half away from zero.
- **Money.** Each vehicle has one reporting `currency`. A cost keeps its source `amount` and `currency`. A purchase in another currency needs an explicit `exchangeRate` (reporting units per source unit) or `reportingAmount` (`reporting_amount_required`, 422); no rate is ever assumed. The reporting currency cannot change once costs exist (`currency_locked`, 409).
- **Statistics.** `GET /v1/vehicles/{id}/stats?from&to` selects intervals by their closing fill. `spend` sums every costed purchase in the window and is separate from efficiency. `costPerDistance` uses only intervals whose purchases all have a cost.
- **Access.** Viewers read; editors and owners write; an archived vehicle is read-only (`vehicle_archived`, 409). Every write locks the vehicle row and writes a `fill_up.*` audit event.

**Naming.** Resource endpoints use camelCase fields. The `auth` endpoints from milestone 1.2 use snake_case. Both are stable within `/v1`; unifying them is a breaking change left for a future major version.
