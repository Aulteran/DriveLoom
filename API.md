# DriveLoom API reference

The complete reference for the DriveLoom HTTP API: how to authenticate, how personal API keys and their permissions work, every endpoint, and the rules for imports, retries, errors and rate limits.

This document describes API **0.10.0**. The contract itself, [`apps/api/openapi/openapi.yaml`](apps/api/openapi/openapi.yaml), is the source of truth; every running instance also serves it (see [Versioning](#versioning-and-the-served-contract)), together with interactive documentation, and the copy your server serves always matches the server you are talking to. If this file and a running server ever disagree, trust the server.

## 1. Overview

DriveLoom is a self-hosted fuel and service tracker. Its API is the one the web client and the Android app use, and the one scripts and integrations can use with a personal API key.

| | |
| --- | --- |
| Base URL | `https://your-host/v1` (replace `your-host` with the address of your instance; every path in the contract begins with `/v1/`) |
| Format | JSON (`application/json`). The exceptions are raw uploads (receipts, vehicle photos), downloads (receipts, photos, CSV and JSON exports) and the served contract. |
| Errors | RFC 9457 problem details (`application/problem+json`), see [Errors](#8-errors) |
| Contract | OpenAPI 3.1, API version `0.10.0` |
| Status | Pre-release. The contract is versioned and tested, but treat it as 0.x. |

### Conventions

- **Decimals are strings.** Every decimal quantity (odometer and volume values, money, exchange rates) is a JSON string such as `"42.375"` and never a JSON number, so no precision is lost. Send strings; read strings.
- **Units travel with the value.** A distance is `{ "value": "84210", "unit": "km" }` (`km` or `mi`), a volume is `{ "value": "41.20", "unit": "l" }` (`l`, `gal_us` or `gal_imp`). Entered values are stored and returned exactly as sent; responses also carry converted `display` values where that helps.
- **Timestamps** are UTC instants in RFC 3339, for example `2026-11-20T08:30:00Z`; responses use millisecond precision (`2026-11-20T08:30:00.000Z`). Service dates (`servicedOn`, `until`, `firstDueOn` and so on) are plain dates, `YYYY-MM-DD`.
- **IDs** are opaque UUIDv7 strings generated by the server. Treat them as opaque.
- **Unknown request fields are rejected** with `422 validation_failed`. Do not send fields you are not sure about. Do ignore response fields you do not know: the server may add some.
- **Request size.** JSON bodies are limited to 64 KiB, except imports (96 MiB, so receipts can be embedded; CSV import text is limited to 8 MiB). Receipts are limited to 10 MiB each and vehicle photos to 5 MiB. Too large is `413 body_too_large`.
- **Request IDs.** Every response to an API-key request carries `X-Request-Id`. You may send your own (up to 64 characters of `A-Z a-z 0-9 . _ -`); it is then echoed back and stored with the key's [activity](#35-activity-history), which makes a write easy to trace. Otherwise the server generates one.
- **Modules.** Service history, maintenance and reminder emails belong to the opt-in *Service* module, which an administrator must switch on for the instance. While it is off, those endpoints answer `404 module_disabled`.
- **Roles still apply.** On a vehicle you are an `owner`, `editor` (shown as "Authorized Manager"), `driver` or `viewer`. Viewers read; drivers add fill-ups and service visits and change only their own; editors edit details and import; only owners manage members, archive, transfer ownership and delete. An API key never exceeds its owner's current role.

### Versioning and the served contract

- `GET /v1/version` returns `{ "server": "...", "api": "0.10.0", "schema": 20 }`. `api` is the contract version, `info.version` of the OpenAPI document, which is semantic versioning (`MAJOR.MINOR.PATCH`). A client can read it at start-up and refuse to run against a server it does not know.
- Every instance serves, without authentication and outside `/v1`:

  | Path | What |
  | --- | --- |
  | `/openapi.yaml` | The OpenAPI 3.1 contract (`application/yaml`), byte-for-byte the file the server was built and tested against |
  | `/openapi.json` | The same contract as JSON |
  | `/docs` | Interactive documentation, rendered by the instance itself from the same contract (no third-party scripts, no CDN, no analytics) |

  These contain no private data and are never cached (`Cache-Control: no-cache`). Because they come from the running server, they always match its version. Prefer them over this file when generating clients.
- Each key-accessible operation in the contract declares `security: [session, apiKey]` and an `x-driveloom-key-policy` extension (`requires`, `dynamic`) that mirrors the table in [section 4.4](#44-permissions-per-operation); operations without `apiKey` in their security are session-only.

## 2. Authentication

There are two ways to call the API. A single request carries exactly one of them.

| | Browser session | API key |
| --- | --- | --- |
| Meant for | The web app and the Android app | Scripts, integrations, automation |
| Credential | `dl_session` cookie (HttpOnly, SameSite=Lax) | `Authorization: Bearer dlk_...` |
| Anti-forgery | `X-CSRF-Token` header on every unsafe request | Not needed |
| Reach | Everything the signed-in person may do | Only what the key was granted, and never the [session-only endpoints](#46-always-session-only) |
| Transport | As the instance is deployed | HTTPS, or the local machine (see below) |

### 2.1 Browser sessions

Sign in with `POST /v1/auth/login` (email and password), `POST /v1/auth/passkeys/login/verify` or OpenID Connect. The response sets the `dl_session` cookie and returns a `csrf_token`:

```json
{ "state": "signed_in", "csrf_token": "kjtGLBs6u5xgKP_gTwESjMuAk5NXA88n" }
```

If a second factor is enrolled the state is `mfa_required` and the sign-in is completed with `POST /v1/auth/mfa/totp` or `POST /v1/auth/mfa/email`. `GET /v1/auth/session` returns the current account and a fresh `csrf_token`.

- Every `POST`, `PUT`, `PATCH` and `DELETE` made with a session must send `X-CSRF-Token: <csrf_token>`, otherwise `403 csrf_failed`.
- If a request carries an `Origin` header (browsers always send one on unsafe requests) it must equal the instance's public origin, otherwise `403 csrf_failed`. This check applies to bearer requests too: `curl` and most HTTP libraries send no `Origin`, which is fine.
- **Recent sign-in ("fresh authentication").** Sensitive operations, including creating, rotating and broadening an API key, need a sign-in or `POST /v1/auth/reauth` (password or authenticator code) within the last 10 minutes. Otherwise they answer `403 reauth_required`.

The session endpoints are listed in [Session-only endpoints](#59-session-only-endpoints). You need a session to create API keys; there is no way to bootstrap a key with another key.

### 2.2 API keys

```sh
curl --fail-with-body \
  -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" \
  https://your-host/v1/me
```

The rules, all enforced before any endpoint runs:

1. **Exactly one `Authorization` header**, of the form `Bearer dlk_` followed by 43 URL-safe characters (the token is 47 characters long). A malformed, repeated, unknown, expired or revoked credential is `401 invalid_api_key` with `WWW-Authenticate: Bearer error="invalid_token"`. The reason is never revealed.
2. **No cookie fallback.** As soon as an `Authorization` header is present the request is an API-key request and only that. If the key is bad the request fails; the session cookie is not tried. Other credential-looking headers (`X-API-Key`, `Api-Key`, `ApiKey`, `X-Auth-Token`, `X-Access-Token`, `X-DriveLoom-Key`, `X-DriveLoom-Token`) and query parameters (`access_token`, `api_key`, `apikey`) are refused the same way. **Never put a key in a URL.**
3. **HTTPS only**, with two exceptions: a request from the local machine (loopback), and a request that reaches the server through a [trusted proxy](#112-operator-and-proxy-notes) that terminated TLS and says so with `X-Forwarded-Proto: https`. Anything else is `403 https_required`, checked before the key is even looked at.
4. **No CSRF token**, since a bearer request is not ambient browser authority. The `Origin` rule from the previous section still applies if you send an `Origin`.
5. **Public endpoints ignore credentials.** `GET /v1/health`, `GET /v1/version` and the sign-in-time endpoints that need no session answer the same with or without an `Authorization` header.
6. **Deny by default.** A key can call only the operations marked "session or API key" in the [endpoint reference](#5-endpoint-reference). On anything else the answer is `403 api_key_not_allowed`, whatever permissions the key holds.
7. An administrator can switch API keys off for the whole instance. A valid key then gets `403 api_keys_disabled`.

### 2.3 Checking a key: `GET /v1/me`

`GET /v1/me` is open to a session and to any valid key and needs no permission. It is the right first call of a script: it proves the key works and shows exactly what the key may do.

```sh
curl --fail-with-body -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" https://your-host/v1/me
```

```json
{
  "user": { "id": "018f3b1e-0000-7000-8000-000000000001", "displayName": "Alex" },
  "authMethod": "api_key",
  "apiKey": {
    "id": "018f3b1e-0000-7000-8000-0000000000a1",
    "name": "Service import (one-off)",
    "permissions": { "vehicle_info": "read", "service": "read_write" },
    "vehicleMode": "selected",
    "vehicleIds": ["018f3b1e-0000-7000-8000-0000000000b1"],
    "vehicleCreate": false,
    "expiresAt": "2026-12-04T16:40:25.382Z"
  }
}
```

With a session, `authMethod` is `"session"` and `apiKey` is `null`. The response reports the key's *configuration* (modules at `none` are omitted; `vehicleIds` is empty for `all_current_future`), not what the owner could do with a session. It deliberately contains no email address, role or vehicle name.

## 3. API keys

A personal API key is a revocable bearer credential with only the access you give it: a level per [permission module](#4-permissions), a set of vehicles, and an expiry. Keys are for scripts and integrations; they are not service accounts, and they are never administrators.

### 3.1 Creating and managing keys

**In the app:** open *Account and security*, scroll to *API keys* and choose *Create API key*. Pick a name, an expiry, the vehicles and a level for each permission. Nothing is selected for you. The key is shown **once**; copy it into a password manager or secret store straight away. The same screen lists your keys (name, prefix, status, permissions, vehicles, created, last used, expiry), and lets you edit, rotate, revoke, remove and review activity. The *Developer access* section links to the interactive docs and the contract.

**Through the API:** the same operations exist as session-only endpoints (you must be signed in with a cookie session; an API key can never manage keys, including itself). Requests need `X-CSRF-Token`; create, rotate and broadening edits need a [recent sign-in](#21-browser-sessions).

| Endpoint | Purpose |
| --- | --- |
| `GET /v1/auth/api-keys` | List your keys |
| `POST /v1/auth/api-keys` | Create a key (returns the token once) |
| `PATCH /v1/auth/api-keys/{id}` | Edit an active key |
| `POST /v1/auth/api-keys/{id}/rotate` | Replace the secret (returns the new token once) |
| `DELETE /v1/auth/api-keys/{id}` | Revoke an active key, or remove an expired or revoked one |
| `POST /v1/auth/api-keys/revoke-all` | Revoke every active key (lockdown) |
| `GET /v1/auth/api-keys/{id}/activity` | History of one key |

Another user's key behaves exactly like a missing one: `404 api_key_not_found`.

#### Create

`POST /v1/auth/api-keys`

| Field | Type | Notes |
| --- | --- | --- |
| `name` | string, required | 1 to 60 characters after trimming, no control characters |
| `expiresIn` | `24h`, `7d`, `30d`, `90d`, `365d`, `never` | Default `30d`. The server computes the expiry in UTC. |
| `permissions` | object | A level per module, for example `{ "fuel": "read_write" }`. A module not listed is `none`. Only [levels the module offers](#41-modules-and-levels) are accepted. `vehicle_create` is not a level (see `vehicleCreate`). |
| `vehicleCreate` | boolean | Default `false`. Allows creating vehicles (`POST /v1/vehicles`, `POST /v1/vehicle-imports`). |
| `vehicleMode` | `selected`, `all_current`, `all_current_future` | Default `selected`. See [vehicle scope](#42-vehicle-scope). |
| `vehicleIds` | array of ids, at most 200 | Only with `selected`; vehicles you can currently access. |

Defaults when a field is left out: no module access, no vehicle creation, `selected` mode with no vehicles, 30 days.

```sh
# Run in a signed-in cookie session; see the worked example for the sign-in.
curl --fail-with-body -b jar.txt -X POST https://your-host/v1/auth/api-keys \
  -H "X-CSRF-Token: ${CSRF}" -H 'Content-Type: application/json' \
  -d '{
        "name": "Fuel logger",
        "expiresIn": "90d",
        "vehicleMode": "selected",
        "vehicleIds": ["018f3b1e-0000-7000-8000-0000000000b1"],
        "permissions": { "vehicle_info": "read", "fuel": "read_write" }
      }'
```

`201 Created`, with `Cache-Control: no-store`:

```json
{
  "id": "018f3b1e-0000-7000-8000-0000000000a2",
  "name": "Fuel logger",
  "prefix": "dlk_v3K7C0hI",
  "status": "active",
  "createdAt": "2026-11-27T16:41:01.956Z",
  "updatedAt": "2026-11-27T16:41:01.956Z",
  "lastUsedAt": null,
  "expiresAt": "2027-02-25T16:41:01.956Z",
  "rotatedAt": null,
  "revokedAt": null,
  "vehicleMode": "selected",
  "vehicleIds": ["018f3b1e-0000-7000-8000-0000000000b1"],
  "permissions": { "vehicle_info": "read", "fuel": "read_write" },
  "vehicleCreate": false,
  "token": "dlk_<43 characters, shown only in this response>"
}
```

Problems: `409 too_many_api_keys` (25 active keys already), `403 api_keys_disabled`, `403 reauth_required`, `422 validation_failed` (unknown module, a level the module does not offer, a vehicle you cannot access, unknown field).

#### List

`GET /v1/auth/api-keys` returns `{ "items": [ ...key objects without a token... ], "apiKeysEnabled": true, "maxActiveKeys": 25 }`, newest first. `status` is `active`, `expired` or `revoked`. Expired keys stay listed until removed. `apiKeysEnabled` is `false` while an administrator has switched keys off. The `prefix` (the first 12 characters of the token) helps you recognise a key; it is not a secret.

#### Edit

`PATCH /v1/auth/api-keys/{id}` accepts the same fields as create, all optional. Fields you do not send stay as they are; `permissions`, when sent, **replaces the whole map** (anything not listed becomes `none`).

```sh
curl --fail-with-body -b jar.txt -X PATCH "https://your-host/v1/auth/api-keys/${KEY_ID}" \
  -H "X-CSRF-Token: ${CSRF}" -H 'Content-Type: application/json' \
  -d '{ "name": "Fuel logger (read only)", "permissions": { "vehicle_info": "read", "fuel": "read" } }'
```

The server compares the old and the new state:

- **Broadening** needs a recent sign-in (`403 reauth_required` otherwise): a higher level on any module (anything that allows an action the old level did not), `vehicleCreate` from `false` to `true`, a vehicle that was not in the old stored set, a switch to a wider vehicle mode (any switch to `all_current_future`), or a later or no expiry. While API keys are switched off for the instance, a broadening edit is `403 api_keys_disabled`.
- **Narrowing and renaming** need only the session and CSRF token.
- A request that changes nothing succeeds and changes nothing.
- `all_current` takes a new snapshot of your vehicles **only when the mode is switched to it**; sending `all_current` for a key that already has it does not refresh the snapshot. `vehicleIds` is only valid with `selected` (and required when switching from `all_current_future` to `selected`).
- An expired or revoked key can never be edited, rotated or reactivated: `409 api_key_not_active`. Create a new key instead.

#### Rotate

`POST /v1/auth/api-keys/{id}/rotate` needs a recent sign-in and an enabled instance. It atomically replaces the secret. The id, name, permissions, vehicles and expiry stay; `lastUsedAt` is cleared; the **old token stops working at once** (there is no grace period). The response is the key object with the new `token`, shown once (`Cache-Control: no-store`). `409 api_key_not_active` for an expired or revoked key.

#### Revoke, remove, revoke all

- `DELETE /v1/auth/api-keys/{id}`: an **active** key is revoked immediately (no fresh sign-in needed). An **expired or revoked** key is removed from the list. Either way the activity history is kept. A second `DELETE` of a revoked key therefore removes it. `204`.
- `POST /v1/auth/api-keys/revoke-all` (empty body or `{}`) revokes every active key at once, also without a fresh sign-in: this is the lockdown button. Response `{ "revoked": 3 }`. Only active keys are touched, so an expired key still shows as expired.

### 3.2 Token format and storage

A key is `dlk_` followed by 43 URL-safe base64 characters (32 random bytes, 256 bits; 47 characters in all). DriveLoom stores only a SHA-256 hash of it plus the 12-character display prefix. The token appears exactly once, in the response that creates or rotates it, and is never shown again, never listed, never written to logs, audit records or backups, and never part of an error message. If you lose a key, rotate or replace it.

### 3.3 Limits

- At most **25 active keys** per account (unexpired and not revoked). Revoked and expired keys do not count. The limit is enforced transactionally, so concurrent creates cannot exceed it (`409 too_many_api_keys`).
- At most 200 vehicles in a `selected` list.
- Names are 1 to 60 characters.

### 3.4 When keys are revoked, and when they are kept

| Event | Effect on your keys |
| --- | --- |
| Sign out, "sign out everywhere", or any other session ending | Kept |
| Ordinary password change; adding or removing a passkey or authenticator | Kept |
| Account recovery by email (`POST /v1/auth/recovery/complete`) | **All active keys revoked** |
| Operator password reset (`node scripts/auth-admin.ts reset-password`) | **All active keys revoked** |
| An administrator disables your account | **All active keys revoked**; enabling the account again does **not** reactivate them |
| You delete your account | Keys deleted; their history keeps only ids and timestamps |
| You use *revoke all* (`POST /v1/auth/api-keys/revoke-all`) | **All active keys revoked** |
| An administrator switches API keys off for the instance | Keys are not touched but stop working; they resume (if still valid) when switched back on |
| A key reaches its expiry | It stops working at that moment; listed as `expired` until removed |
| A backup is restored | **All keys are cleared** (see below) |

Revocations caused by an account change happen in the same database transaction as the change itself.

### 3.5 Activity history

`GET /v1/auth/api-keys/{id}/activity?limit=50&before=<activity id>` returns, newest first, what happened with one key, also after the key was removed:

```json
{
  "items": [
    {
      "id": "018f3b1e-0000-7000-8000-0000000000c1",
      "occurredAt": "2026-11-27T16:40:40.901Z",
      "action": "service_visit.import",
      "keyName": "Service import (one-off)",
      "targetType": "service_visit",
      "targetIds": ["018f3b1e-0000-7000-8000-0000000000d1"],
      "vehicleId": "018f3b1e-0000-7000-8000-0000000000b1",
      "requestId": "018f3b1e-0000-7000-8000-0000000000e1",
      "metadata": { "total": 1, "part": 1 },
      "redacted": false
    }
  ],
  "nextBefore": null
}
```

- `limit` is 1 to 200 (default 50). Pass `nextBefore` as `before` for the next page; `nextBefore` is `null` at the end.
- It records key management (`created`, `updated`, `rotated`, `revoked`, `revoked_all`, `removed`) and **successful writes** made with the key (for example `fill_up.create`, `service_visit.create`, `service_visit.update`, `service_attachment.add`, `maintenance_task.create`, `vehicle.create`, `vehicle.import` and, per record kind, `fill_up.import`, `service_visit.import`, `service_attachment.import`, `maintenance_task.import`).
- **Reads are never logged.** A dry run records nothing. Exports are not recorded as key activity.
- Bulk imports record a summary plus the ids of every created record, in rows of up to 200 ids (`metadata.part` numbers the rows).
- `keyName` is the name at the time of the event, so a renamed key stays attributable.
- If the vehicle in an event is one you can no longer access, the event is returned with `redacted: true` and without vehicle or target ids.
- Only you, the owner, can read it.

### 3.6 Instance switch (administrators)

An administrator can turn API keys off for the whole instance under *Administration, API keys* (`GET` / `PUT /v1/admin/settings/api-keys`, body `{ "enabled": false }`). The default is on, including on installs that existed before API keys. While off:

- every key request fails with `403 api_keys_disabled` (only for an otherwise valid key; invalid keys still get the generic `401`);
- creating keys, rotating them and broadening edits are refused with `403 api_keys_disabled`;
- owners can still list their keys, read activity, revoke, and narrow keys.

Turning it back on resumes only keys that are still valid (not expired, not revoked). The change is audited as `admin.api_keys_changed`. Administrators never see another person's token.

### 3.7 Backups and restores

- Backup files (`node scripts/backup.ts create ...`) **never contain** API keys, their permissions and vehicle bindings, idempotency records or preview tokens.
- **Restoring a backup clears every key** on the target instance, and a backup file that contains key credentials is rejected. After a restore, create new keys.
- Key *activity history* is kept like the audit log: it survives backups and restores, has no foreign keys, and never authenticates anything.
- A raw database snapshot (`pg_dump`, a volume copy) is different: it does hold key **hashes** (not tokens). Invalidate or delete the `api_keys` rows before you share or expose a snapshot.

## 4. Permissions

Every key-accessible operation needs three things at once, on top of a valid key and an enabled instance:

1. The vehicle must be **in the key's scope** (and the owner must still be a member of it).
2. The key must hold the **permission** the operation needs, at a level that allows its action.
3. The owner's own **vehicle role and the module switches** must allow it. A key can only narrow what its owner may do.

### 4.1 Modules and levels

A key holds a level per module. `none` is the default for every module. Only the levels a module actually offers are accepted; anything else is `422 validation_failed`.

| Level | Allows |
| --- | --- |
| `none` | Nothing |
| `read` | Read |
| `read_write` | Read, create and update |
| `full` | Read, create, update and **delete** |

| Module | Levels offered | What it covers |
| --- | --- | --- |
| `vehicle_info` | `none`, `read` | List and read vehicles, read the vehicle photo; the entry permission of import and export |
| `vehicle_settings` | `none`, `read_write`, `full` | Edit vehicle details and set or replace the photo (`update`); remove the photo (`delete`). Reading belongs to `vehicle_info`. |
| `vehicle_create` | boolean `vehicleCreate`, not a level | Create vehicles, directly or by import |
| `fuel` | `none`, `read`, `read_write`, `full` | Fill-ups (fuel purchases) |
| `service` | `none`, `read`, `read_write`, `full` | Service visits, their items and receipt attachments |
| `maintenance` | `none`, `read`, `read_write`, `full` | Maintenance catalog, status, tasks, snoozes, presets |
| `notifications` | `none`, `read`, `read_write` | Reminder-email settings for a vehicle and your own preference |
| `statistics` | `none`, `read` | Derived fuel statistics |

Deletion is deliberately separate: a `read_write` key can add and correct records but never remove them. Operations are classified by what they *do*, not by their HTTP verb. A `PATCH` that removes an item from a service visit needs `delete`; a `POST` dry-run import needs the grants of the import it previews.

### 4.2 Vehicle scope

A key's `vehicleMode` decides which of your vehicles it can reach:

| Mode | Scope |
| --- | --- |
| `selected` (default) | Exactly the vehicles listed in `vehicleIds` (up to 200). Nothing is ever added automatically. |
| `all_current` | A snapshot of the vehicles you can access at the moment you grant it (at creation, or when the key is switched to this mode). Vehicles you get access to later are not included. |
| `all_current_future` | Every vehicle you can access, now and in the future. Dynamic and broad: use it deliberately. `vehicleIds` is empty for such a key. |

Scope is the stored selection **and** your live membership: if you lose access to a vehicle (or leave it, or it is deleted) the key loses it at once. Your role on the vehicle always applies as well, including archive restrictions.

`vehicleCreate` permits creating vehicles but does not grant access outside the scope: a vehicle created by a key joins its scope **only in `all_current_future` mode**. A `selected` or `all_current` key that creates a vehicle receives `201` and then `404 vehicle_not_found` when it tries to read it. (You, in the app, own the vehicle as usual.)

### 4.3 404 versus 403

- A vehicle **outside the key's scope** (or one you are not a member of) is the ordinary `404 vehicle_not_found`, before any permission is mentioned. This is deliberate: a key cannot probe which vehicles exist.
- A vehicle **in scope** but a missing permission is `403 insufficient_scope`. The problem carries a `required` member naming the first missing permission, for example `"required": "service.delete"`.
- The owner's role refusing the action is `403 forbidden`; a switched-off Service module is `404 module_disabled`; an archived vehicle refuses writes with `409 vehicle_archived`.
- An operation that is session-only is `403 api_key_not_allowed`.

### 4.4 Permissions per operation

Each operation in the [endpoint reference](#5-endpoint-reference) states what it needs. The same information is machine-readable in the contract as `x-driveloom-key-policy.requires` (every listed permission must be held) and `dynamic`.

| Area | Operation | Permission(s) needed |
| --- | --- | --- |
| Vehicles | `GET /v1/vehicles`, `GET /v1/vehicles/{vehicleId}` | `vehicle_info.read` |
| | `POST /v1/vehicles` | `vehicle_create` |
| | `PATCH /v1/vehicles/{vehicleId}` | `vehicle_settings.update` |
| | `GET .../image` | `vehicle_info.read` |
| | `PUT .../image` | `vehicle_settings.update` |
| | `DELETE .../image` | `vehicle_settings.delete` |
| Fuel | list, get fill-ups | `fuel.read` |
| | create | `fuel.create` |
| | update | `fuel.update` |
| | delete | `fuel.delete` |
| | `GET .../stats` | `statistics.read` **and** `fuel.read` |
| Service | list, get visits; download a receipt | `service.read` |
| | create a visit; upload a receipt | `service.create` |
| | update a visit; rename a receipt | `service.update` |
| | delete a visit; delete a receipt | `service.delete` |
| Maintenance | `GET /v1/maintenance-catalog` | `maintenance.read` |
| | status, list/get tasks, list presets | `maintenance.read` **and** `service.read` **and** `fuel.read` |
| | create task, apply preset | `maintenance.create` **and** `service.read` **and** `fuel.read` |
| | update task, set snooze | `maintenance.update` **and** `service.read` **and** `fuel.read` |
| | clear snooze | `maintenance.delete` **and** `service.read` **and** `fuel.read` |
| | delete task | `maintenance.delete` **and** `service.update` |
| Notifications | `GET .../notification-settings` | `notifications.read` |
| | `PUT .../notification-settings`, `PUT .../notification-preferences/me` | `notifications.update` |
| Portability | `GET .../export` | `vehicle_info.read` plus one grant per section, see [section 6](#6-imports-and-exports-with-api-keys) |
| | `POST .../import` | `vehicle_info.read` plus the write grant of every section in the payload |
| | `POST /v1/vehicle-imports` | `vehicle_create` plus the write grant of every section in the payload |
| Identity | `GET /v1/me` | any valid key |

**Why the extra requirements.** Maintenance task status, due dates and "last completed" are computed from service history and odometer readings (which come from fill-ups and service visits), so every response that carries them also needs `service.read` and `fuel.read`; otherwise a key could read service or fuel data through the back door. Statistics are derived from fill-ups and need `fuel.read` for the same reason. Deleting a maintenance task clears the link on service items that completed it, which changes service records, hence `service.update`. The catalog holds only names and illustrative defaults, so it needs `maintenance.read` alone.

#### Dynamic requirements

Some effects depend on the request body, so they are checked while the request runs (and again inside the write's transaction, so a revocation or a permission reduction cannot be outrun by a request already in flight):

- **Removing nested records.** `PATCH` of a service visit with `items` replaces the whole item list. Stored items are matched to the new list one-for-one by name (case-insensitive, whitespace-normalised). Dropping or renaming an item counts as removing it and needs `service.delete` as well as `service.update`. Editing cost, category, notes or the task link of an item, adding items or reordering them needs only `service.update`. A patch without `items` never needs `delete`.
- **Task links.** A service item may point at a maintenance task with `taskId`. Choosing a task needs `maintenance.read`: on create when any item has a `taskId`; on `PATCH` when a task link is added, changed or removed (including by omitting `taskId` on an item that had one, or by dropping or renaming a linked item). An item that keeps its stored link needs nothing extra. Changing the *task itself* needs the maintenance grants.
- **Preset apply.** The effects are worked out from the request alone: `maintenance.create` always (with `service.read` and `fuel.read`); `onDuplicate: "link"` also needs `maintenance.update` (every level that allows create already allows update, so this never differs today); `baseline.linkServiceItemId` also needs `service.update`. `?preview=true` needs exactly the grants of the commit it previews.
- **Notification settings.** For a key, responses never list other people. See [below](#notification-settings-redaction).
- **Imports and exports** check the grants of every section the payload contains; see [section 6](#6-imports-and-exports-with-api-keys).

#### Notification settings redaction

`GET` and `PUT /v1/vehicles/{vehicleId}/notification-settings` answer an API key with **only the key owner's own recipient entry** plus `otherRecipientCount` (a number); other members' names and email addresses are never returned. `recipientUserIds` cannot be set by a key (`403 api_key_not_allowed`, even for an empty list), because choosing recipients needs the member list. Switching reminders on or off (`emailEnabled`) and `followUpDays` work.

### 4.5 Roles, modules and states that still apply

Whatever the key allows, the owner's rights decide first:

- A **viewer** cannot write even with a `full` key; a **driver** can add fill-ups and service visits but change only the ones they recorded; **editors** and **owners** can edit; imports need editor or owner.
- The **Service module** gate applies: service, maintenance and notification endpoints answer `404 module_disabled` while it is off. Imports of service visits or maintenance tasks by a key are refused likewise; session imports into a vehicle are still allowed while the module is off, so recorded data is never stranded.
- **Archived vehicles** refuse writes (`409 vehicle_archived`).
- Business rules are unchanged: odometer sequencing, duplicate detection, attachment limits and so on.

### 4.6 Always session-only

These can never be done with an API key (`403 api_key_not_allowed`), whatever it holds:

- every `/v1/auth/*` endpoint: sign-in, second factors, passkeys, OIDC, password and recovery, sessions, account changes and deletion, and **API-key management itself**;
- every `/v1/admin/*` endpoint;
- permanent vehicle deletion, archiving and unarchiving, ownership transfer, and member add, role change and removal (including the member listing);
- friends and vehicle comparison (opt-in, comparisons), account-wide preferences, the per-vehicle Service-page visibility preference, and the make and model suggestions (`GET /v1/vehicle-identities`).

## 5. Endpoint reference

Every operation in the contract is listed below, grouped by area. Sections 5.2 to 5.8 cover the operations an API key may call, with fuller detail and examples. Section 5.9 lists the session-only operations, which are included for completeness.

### 5.1 How to read an entry

- **Auth** is either "session or API key" or "session only".
- **Key permission** is what a key must hold (all of them), or "session only". `403 insufficient_scope` is returned when one is missing, `404 vehicle_not_found` when the vehicle is outside the key's scope.
- Path parameters are written `{like this}`. `{vehicleId}` is a vehicle id from `GET /v1/vehicles`.
- Every key-accessible operation can also answer `401 invalid_api_key`, `403 api_keys_disabled`, `403 https_required`, `403 insufficient_scope`, `404 vehicle_not_found` (vehicle routes) and `429 rate_limited`; these are not repeated in each entry. Every operation can answer `422 validation_failed` when the request is malformed. Sessions can additionally get `401 unauthenticated` and `403 csrf_failed`.
- Examples use `${DRIVELOOM_API_KEY}` (a key in an environment variable) and `${VEHICLE_ID}`, and show the body of the response trimmed to what matters. Identifiers in examples are made up.

### 5.2 System and identity

#### `GET /v1/health`

Liveness and database readiness. No authentication. `200 { "status": "ok", "database": "ok" }`, or `503` problem when the database is unreachable.

#### `GET /v1/version`

Server, API and schema versions. No authentication.

```json

`api` is the contract version (`info.version` of the OpenAPI document), `server` the release, `schema` the latest applied database migration.

Who the caller is and how they authenticated. **Auth:** session or API key. **Key permission:** none (any valid key). See [Checking a key](#23-checking-a-key-get-v1me) for the response.

### 5.5 Service history and receipts

Needs the Service module (else `404 module_disabled`). A visit has one or more items; receipts (PDF, JPEG or PNG files) attach to the visit.

#### `GET /v1/vehicles/{vehicleId}/service-visits`

Service visits, newest first (service date, then record creation). **Auth:** session or API key. **Key permission:** `service.read`.

Query: `limit` (1 to 200, default 50), `cursor` (the `nextCursor` of the previous page), `from` and `to` (service dates, inclusive), `q` (case-insensitive text search in provider, notes and item names and notes, up to 100 characters), `category` (visits having an item of that category). `200 { "items": [ServiceVisit], "nextCursor": null }`.

#### `POST /v1/vehicles/{vehicleId}/service-visits`

| Field | Type | Notes |
| --- | --- | --- |
| `servicedOn` | date, required | The day the work was done |

| `provider` | string or null, up to 120 | |

| `totalCost` | decimal string or null | In the vehicle's currency. Omitted or `null` means unknown, `"0"` means known to be free. Not checked against item costs. |

One visit. **Auth:** session or API key. **Key permission:** `service.read`. `200 ServiceVisit`; `404 service_visit_not_found`.

#### `PATCH /v1/vehicles/{vehicleId}/service-visits/{visitId}`

Correct a visit (owner or editor; a driver only their own). **Auth:** session or API key. **Key permission:** `service.update`, plus `service.delete` when the patch removes or renames a stored item, plus `maintenance.read` when it adds, changes or removes a task link (see [dynamic requirements](#dynamic-requirements)). Body: any create field, at least one. When `items` is sent it **replaces the whole list**. The merged visit is validated again as a whole. `200 ServiceVisit`.

For example, a key with `service` at `read_write` that sends an `items` list lacking one of the stored items is answered `403 insufficient_scope` with `"required": "service.delete"`, and nothing is changed.

Attach a receipt or invoice to a visit. **Auth:** session or API key. **Key permission:** `service.create`. Supports [`Idempotency-Key`](#7-idempotency-key).

Query: `fileName` (display name, reduced to a base name, up to 200 characters).

Limits: 10 MiB per file (`413`), 10 files per visit (`422 attachment_limit`). A key cannot attach a file the visit already holds (same SHA-256): `409 attachment_duplicate`, with the existing `attachmentId`. Counts towards the stricter [upload rate limit](#9-rate-limits).

```

```json

```

Download an attachment. **Auth:** session or API key. **Key permission:** `service.read`. `200` with the file bytes and `Content-Disposition: attachment` (add `?inline=1` to get `inline`, for previews). Always sent with `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store` and a restrictive `Content-Security-Policy`.

Rename an attachment. **Auth:** session or API key. **Key permission:** `service.update`. Body `{ "fileName": "new-name.pdf" }`. `200 ServiceAttachment`.

### 5.6 Maintenance

A maintenance task is a recurring (or one-time) reminder such as "Oil change every 12 months or 15 000 km". Its status (`ok`, `due_soon`, `overdue`, `no_baseline`, `unknown_reading`, `completed`) is **computed on every read** from the task, the service items linked to it and the latest odometer reading, never stored. That is why these operations need `service.read` and `fuel.read` as well. Needs the Service module (else `404 module_disabled`).

#### `GET /v1/maintenance-catalog`

Common service types (names only) and the illustrative reminder defaults. **Auth:** session or API key. **Key permission:** `maintenance.read`. `200 { "items": [ { "key": "oil_change", "name": "Oil change" }, ... ], "defaults": { "leadDays": 30, "leadDistance": { "value": "500", "unit": "km" }, "staleReadingDays": 90 } }`. DriveLoom ships no manufacturer intervals; the defaults only decide when a task counts as "due soon".

#### `GET /v1/vehicles/{vehicleId}/maintenance-status`

Counts of tasks by status, for the Service page header. **Auth:** session or API key. **Key permission:** `maintenance.read`, `service.read`, `fuel.read`.

```json
{
  "counts": { "total": 1, "overdue": 0, "due_soon": 0, "ok": 0, "no_baseline": 1, "unknown_reading": 0, "completed": 0, "snoozed": 0, "needsAttention": 0, "remindersActive": 0 },
  "reading": { "odometer": { "value": "85200", "unit": "km" }, "on": "2026-11-25", "source": "fuel", "stale": false },
  "defaults": { "leadDays": 30, "leadDistance": { "value": "500", "unit": "km" }, "staleReadingDays": 90 }
}
```

`reading` is the latest known odometer (from fill-ups and service visits), or `null`; `stale` is `true` when it is older than `defaults.staleReadingDays`.

#### `GET /v1/vehicles/{vehicleId}/maintenance-tasks`

Tasks with their computed status, oldest first. **Auth:** session or API key. **Key permission:** `maintenance.read`, `service.read`, `fuel.read`. Query: `includeArchived=true`. `200 { "items": [MaintenanceTask] }`.

#### `POST /v1/vehicles/{vehicleId}/maintenance-tasks`

Add a task (owner or editor). **Auth:** session or API key. **Key permission:** `maintenance.create`, `service.read`, `fuel.read`. Supports [`Idempotency-Key`](#7-idempotency-key).

| Field | Notes |
| --- | --- |
| `name` | 1 to 120 characters; may be omitted when `catalogKey` is given |
| `catalogKey` | A key from the catalog; a label only, it brings no interval |
| `recurring` | Default `true`. A repeating task needs `intervalDays` or `intervalMonths` (not both), `intervalDistance`, or both kinds; whichever is reached first makes it due. A one-time task has no interval and needs `firstDueOn` or `firstDueOdometer`. |
| `intervalDays` | 1 to 36500 |
| `intervalMonths` | 1 to 1200 calendar months |
| `intervalDistance` | `{ value, unit }`, greater than zero |
| `firstDueOn`, `firstDueOdometer` | Used until the task is first completed |
| `baselineKind`, `baselineOn`, `baselineOdometer` | `reported` (you say when and at what odometer it was last done; scheduled like a completion) or `tracking` (start tracking now; never counts as `ok`). Recurring tasks only; `baselineOn` is today or earlier. |
| `remindersEnabled` | Email reminders for this task, default `true` |
| `notes` | Up to 500 |

At most 200 tasks per vehicle.

```sh
curl --fail-with-body -X POST "https://your-host/v1/vehicles/${VEHICLE_ID}/maintenance-tasks" \
  -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: task-oil-1' \
  -d '{ "name": "Oil change", "intervalMonths": 12, "intervalDistance": { "value": "15000", "unit": "km" } }'
```

`201 MaintenanceTask`: the task fields plus the computed `status`, `dueOn`, `dueOdometer`, `daysUntilDue`, `distanceUntilDue`, `baseline` (`completion`, `reported`, `tracking`, `first_due`, `none`), `distanceBaselineMissing`, `readingStale`, `lastCompleted`, `snoozed`, `snoozes`, `reminderSuppressed`, `needsAttention`. A fresh task without any completion or baseline has `status: "no_baseline"`.

#### `GET /v1/vehicles/{vehicleId}/maintenance-tasks/{taskId}`

One task. **Auth:** session or API key. **Key permission:** `maintenance.read`, `service.read`, `fuel.read`. `200 MaintenanceTask`; `404 maintenance_task_not_found`.

#### `PATCH /v1/vehicles/{vehicleId}/maintenance-tasks/{taskId}`

Change or archive a task (owner or editor). **Auth:** session or API key. **Key permission:** `maintenance.update`, `service.read`, `fuel.read`. Body: any create field plus `archived` (a flag that hides the task without deleting it or its history; it is not a removal), at least one field. The merged task is validated again. `200 MaintenanceTask`.

#### `DELETE /v1/vehicles/{vehicleId}/maintenance-tasks/{taskId}`

Delete a task and its snoozes (owner or editor). Service items that completed the task are kept; their `taskId` becomes `null`. **Auth:** session or API key. **Key permission:** `maintenance.delete` **and** `service.update`. `204`.

#### `PUT /v1/vehicles/{vehicleId}/maintenance-tasks/{taskId}/snooze`

Snooze a task's reminders; replaces the snooze of that scope. **Auth:** session or API key. **Key permission:** `maintenance.update`, `service.read`, `fuel.read`. Query: `scope` is `personal` (default; any member) or `vehicle` (owner or editor; seen by every member). Body: `until` (a date, today or up to 3650 days ahead), `untilOdometer`, `additionalDistance` (all `{ value, unit }` for the distances), and `reason` (up to 200). Give `until`, `untilOdometer` or `additionalDistance`, alone, or `until` with a distance. `additionalDistance` is converted **once, now**, to an absolute odometer target using the latest known reading (`422 no_odometer_reading` when there is none).

A snooze only mutes reminders: it never reschedules or completes a task and never changes `status`, `dueOn` or `dueOdometer`.

```sh
curl --fail-with-body -X PUT \
  "https://your-host/v1/vehicles/${VEHICLE_ID}/maintenance-tasks/${TASK_ID}/snooze?scope=personal" \
  -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" -H 'Content-Type: application/json' -d '{ "until": "2026-12-15" }'
```

`200 MaintenanceTask` (with `snoozed` set).

#### `DELETE /v1/vehicles/{vehicleId}/maintenance-tasks/{taskId}/snooze`

Clear the snooze of the given scope (nothing to clear is not an error). **Auth:** session or API key. **Key permission:** `maintenance.delete`, `service.read`, `fuel.read`. Query: `scope` as above. `200 MaintenanceTask`.

#### `GET /v1/vehicles/{vehicleId}/maintenance/presets`

Community maintenance presets that match this vehicle (advisory templates bundled with the server, never fetched from elsewhere). **Auth:** session or API key. **Key permission:** `maintenance.read`, `service.read`, `fuel.read`. Query: `market` (default `us`). `200 { "market": "us", "vehicle": { "make": ..., "model": ..., "year": ... }, "missing": [], "canApply": true, "items": [ ... ] }`. `missing` names what to ask the owner for when make, model or year is unknown; no match is an empty `items`. Each preset task says whether the vehicle already has it (`alreadyImported`), has a similar typed-in task (`existingTaskMatch`) and which unlinked service items look like it (`suggestedServiceItems`, never linked unless you choose one).

#### `POST /v1/vehicles/{vehicleId}/maintenance/presets/{presetId}/apply`

Import selected preset tasks as maintenance tasks (owner or editor); all or nothing in one transaction. **Auth:** session or API key. **Key permission:** `maintenance.create`, `service.read`, `fuel.read`; `onDuplicate: "link"` also `maintenance.update`; `baseline.linkServiceItemId` also `service.update`.

Query `preview=true` validates and works out every result and status exactly as an apply would, then discards it (nothing is stored; `taskId` is `null` for tasks that would be created). A preview needs exactly the grants of the apply.

Body: `variant` (required when the preset has `needsQualifier` variants), and `tasks`: a non-empty array of `{ "presetTaskId": "...", "overrides": { "intervalMonths", "intervalDistance" }, "baseline": { "kind": "reported" | "tracking" | "none", "on", "odometer", "linkServiceItemId" }, "onDuplicate": "skip" | "link" }`.

Reminder emails are **off** (`remindersEnabled: false`) on imported tasks until the owner turns them on, and nothing is written to odometer or fuel records. A task the vehicle already made from the same preset task is `skipped` (`already_imported`); a similar typed-in task is `skipped` (`existing_task`) or, with `onDuplicate: "link"`, gets only the preset's provenance attached. `200`:

```json
{
  "presetId": "...", "presetVersion": 1, "variant": null, "preview": true,
  "reading": { "odometer": { "value": "85200", "unit": "km" }, "on": "2026-11-25", "source": "fuel", "stale": false },
  "results": [ { "presetTaskId": "...", "result": "created", "reason": null, "taskId": null, "name": "...", "status": "no_baseline", "baseline": "none", "remindersEnabled": false } ]
}
```

`result` is `created`, `linked` or `skipped`. Problems: `404 maintenance_preset_not_found`, `422 maintenance_preset_not_applicable` (the preset does not match the vehicle), `422 maintenance_preset_variant_required`, `409 vehicle_archived`.

## 6. Imports and exports with API keys

A vehicle can be exported to, and imported from, a portable file. The same operations work for sessions and for keys; for keys the permission model is stricter so that a key can never move data it is not allowed to read or write.

### 6.1 The formats

**CSV** (`format=csv`) carries fill-ups only, one row per purchase, with the values and units as entered. Columns: `occurred_at`, `odometer`, `odometer_unit`, `volume`, `volume_unit`, `full`, `missed_previous`, `cost_amount`, `cost_currency`, `exchange_rate`, `reporting_amount`, `reporting_currency`, `notes`. The first five are required. At most 5000 rows; an unknown or repeated column is `422 import_malformed`. Text cells that a spreadsheet could read as a formula are prefixed with an apostrophe on export.

**JSON** (`format=json`) is the versioned document `driveloom.vehicle`, version `1`:

```json
{
  "format": "driveloom.vehicle",
  "version": 1,
  "exportedAt": "2026-11-27T16:41:08.000Z",
  "vehicle": { "name": "Daily", "make": "Toyota", "model": "Corolla", "year": 2019, "odometerUnit": "km", "currency": "EUR" },
  "fillUps": [ { "occurredAt": "2026-11-20T08:30:00Z", "odometer": { "value": "84500", "unit": "km" }, "volume": { "value": "41.20", "unit": "l" }, "full": true, "missedPrevious": false, "cost": null, "notes": "" } ],
  "maintenanceTasks": [ { "ref": "oil", "name": "Oil change", "recurring": true, "intervalMonths": 12 } ],
  "serviceVisits": [
    {
      "servicedOn": "2026-03-14",
      "odometer": { "value": "84210", "unit": "km" },
      "provider": "Corner Garage",
      "totalCost": "189.90",
      "externalId": "garage-2026-0314-001",
      "items": [ { "name": "Oil and filter change", "category": "scheduled", "cost": "119.90", "taskRef": "oil" } ],
      "attachments": [ { "fileName": "invoice-0314.pdf", "contentType": "application/pdf", "sha256": "<hex>", "data": "<base64>" } ]
    }
  ],
  "omittedSections": []
}
```

- The file contains **no ids, members or users**, so it moves between instances and lands under the importing person's own permissions. Plate and VIN are included when set.
- `maintenanceTasks` carry a file-local `ref` (1 to 40 characters of `A-Z a-z 0-9 _ -`); service items point at them with `taskRef`. Only vehicle-wide snoozes travel; personal snoozes never do. At most 200 tasks.
- `serviceVisits` embed each receipt as base64 (`fileName`, `contentType`, `sha256`, `data`; up to 10 files of 10 MiB per visit), so a vehicle with many receipts makes a large file. At most 5000 visits and 5000 fill-ups.
- Both optional sections were added without a version bump: older files lack them, and a server imports whatever it finds.

### 6.2 Exports with a key

`GET /v1/vehicles/{vehicleId}/export?format=csv|json` needs `vehicle_info.read`. A key's export contains **only the sections it may read**:

| Section | Needs |
| --- | --- |
| `vehicle` (details) | `vehicle_info.read` (always) |
| `fillUps` | `fuel.read` |
| `serviceVisits` (with items and receipts) | `service.read` and the Service module on |
| `maintenanceTasks` | `maintenance.read` and the Service module on |

A section the key may not read is **left out entirely** (never an empty list that would look authoritative) and named in `omittedSections`. In a key's export `omittedSections` is always present (an empty array when nothing was left out); session exports never have it. A visit item's `taskRef` is dropped when the tasks section is omitted, so nothing leaks through the reference. CSV is fill-ups only and needs `fuel.read` (`403 insufficient_scope` without it).

```sh
curl --fail-with-body -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" \
  "https://your-host/v1/vehicles/${VEHICLE_ID}/export?format=json" -o vehicle.json
jq '.omittedSections' vehicle.json     # for example ["fillUps","maintenanceTasks"]
```

Exports are reads: they are audited as before but never recorded as key activity, and they share the stricter per-key [rate limit](#9-rate-limits).

A scoped file imports back into the same or another vehicle: a missing `fillUps` is accepted exactly when `omittedSections` lists it.

### 6.3 Imports with a key

Two operations:

| Operation | Body | Target |
| --- | --- | --- |
| `POST /v1/vehicles/{vehicleId}/import` | `{ "format": "csv" \| "json", "data": ..., "dryRun": true, "previewToken": "..." }` | An existing vehicle (editor or owner, not archived) |
| `POST /v1/vehicle-imports` | `{ "data": { ...driveloom.vehicle... }, "dryRun": true, "previewToken": "..." }` | A **new** vehicle owned by the caller (JSON only) |

- `data` is the CSV text, or the JSON export document (an object, not a string).
- A JSON `data` needs `format`, `version`, a `vehicle` object (required; **ignored** when importing into an existing vehicle, which never changes its details) and a `fillUps` list (required unless `omittedSections` lists `fillUps`; `[]` is fine). `serviceVisits` and `maintenanceTasks` are optional.
- **`dryRun` defaults to `true`.** A dry run runs exactly the statements of a commit and rolls them back; it writes no records, no audit and no activity. A commit (`"dryRun": false`) is all-or-nothing: if any row is invalid nothing is imported and the answer is `422 import_invalid`, whose problem carries the `report`.
- Purchases that already exist (same instant and odometer reading) are skipped and counted in `duplicates`, so importing the same file twice changes nothing.
- Limits: JSON bodies up to 96 MiB (so receipts fit), CSV text up to 8 MiB, 5000 rows, 100 errors listed.

#### Every section must be allowed, dry runs included

A key's import is checked against everything the payload **contains**, before anything is written, **also for a dry run**:

| The payload contains | The key must hold |
| --- | --- |
| Any `fillUps` (or CSV rows) | `fuel.create` |
| Any `serviceVisits` (items and receipts included), and the Service module on | `service.create` |
| Any `maintenanceTasks`, and the Service module on | `maintenance.create` |
| Any visit item with a `taskRef` | `maintenance.read` |
| A new vehicle (`POST /v1/vehicle-imports`) | `vehicle_create` |
| Always, into an existing vehicle | `vehicle_info.read` |

If anything is missing, the **whole request is refused**: `403 insufficient_scope`, `required` naming the first missing permission and `missing` listing all of them. An empty section needs nothing. For example:

```json
{
  "type": "about:blank", "title": "Insufficient scope", "status": 403, "code": "insufficient_scope",
  "detail": "This API key does not allow everything this import contains, so nothing was imported. Missing: fuel.create, maintenance.create, maintenance.read.",
  "required": "fuel.create",
  "missing": ["fuel.create", "maintenance.create", "maintenance.read"]
}
```

Grants, the owner's role and the module gates are read again inside the commit's transaction, so a revocation or reduction since the request began wins.

### 6.4 Dry run, then commit: the preview token

A key may not commit blindly. The flow:

1. **Dry run.** Send the import with `"dryRun": true` (or without `dryRun`). If nothing in it is invalid, the report carries a `previewToken` (`dlp_` followed by 32 characters) and `previewExpiresAt`. With any invalid row there is no token: fix the file and dry-run again.
2. **Commit.** Send **the identical** `format` and `data` with `"dryRun": false` and `"previewToken": "<the token>"`. Add an [`Idempotency-Key`](#7-idempotency-key) so a retry after a network failure cannot import twice.

The token is bound to **the key, the target and the exact payload**:

- It is valid for **15 minutes** and can be used **once**.
- The target is `this vehicle` (for `/v1/vehicles/{vehicleId}/import`) or `a new vehicle` (for `/v1/vehicle-imports`); a token from one cannot commit the other, or another vehicle.
- The payload is compared as a canonical JSON digest of `format` and `data` (key order does not matter, `dryRun` and `previewToken` are not part of it). Any change to the data needs a new dry run.
- It is consumed inside the commit transaction. A commit that fails and rolls back leaves it usable; one that succeeds uses it up.

| Problem | Meaning |
| --- | --- |
| `409 preview_required` | A key committed without a `previewToken` |
| `409 preview_mismatch` | The token is unknown or already used, or belongs to another key, another vehicle or a different payload |
| `409 preview_expired` | The preview is older than 15 minutes; dry-run again |

Sessions need no token and have no binding.

### 6.5 The import report

```json
{
  "dryRun": true,
  "committed": false,
  "summary": { "total": 0, "created": 0, "duplicates": 0, "invalid": 0 },
  "errors": [],
  "serviceVisits": {
    "total": 1, "created": 1, "duplicates": 0, "invalid": 0,
    "records": [ { "row": 1, "externalId": "garage-2026-0314-001", "outcome": "created", "visitId": "018f3b1e-0000-7000-8000-0000000000d1" } ]
  },
  "maintenanceTasks": { "total": 1, "created": 1, "duplicates": 0, "invalid": 0 },
  "previewToken": "dlp_<32 characters>",
  "previewExpiresAt": "2026-11-27T16:55:35.096Z"
}
```

- `summary` counts **fill-ups** (CSV rows or `fillUps`), plus the invalid counts of every section. `serviceVisits` and `maintenanceTasks` have their own counters and are present when the file carried those sections. A new vehicle commit also returns the created `vehicle`.
- `errors` lists up to 100 problems, each `{ row, code, message }`; `row` counts from 1.
- In a **dry run** the `visitId`s in `serviceVisits.records` are placeholders for rows that were rolled back; only a commit's ids exist.
- `committed` is `true` only for a commit that wrote.

### 6.6 New-vehicle imports

`POST /v1/vehicle-imports` creates a vehicle owned by the caller from a JSON export, applying the file's `vehicle` block (name, make, model, year, plate, VIN, `odometerUnit`, `currency`). A key needs `vehicle_create` **and** the write grant of every section in the file. The vehicle is created and the report includes it. As with `POST /v1/vehicles`, the new vehicle joins the key's scope **only in `all_current_future` mode**; with any other mode the key can neither read nor re-import into it afterwards (the owner sees it in the app). A dry run creates nothing.

### 6.7 Duplicates: `externalId` and `possibleDuplicates`

Service visits have no natural unique key (two real visits on one day can look alike), so DriveLoom never treats "same date" as "same visit". Give each visit a stable **`externalId`** (its id in the system it comes from; up to 200 characters, unique per vehicle) and re-imports become safe:

- An `externalId` already stored with **identical content** (all fields, with money and distances compared numerically, and every incoming receipt's SHA-256 already attached) is **skipped** and counted in `serviceVisits.duplicates`, with `outcome: "duplicate"` in `serviceVisits.records`.
- An `externalId` already stored with **different content** is a **conflict**: counted in `invalid` and in `serviceVisits.conflicts`, listed in `errors` with code `external_id_conflict`, and nothing is imported (a commit is `422 import_invalid`). Resolve it in the source or edit the stored visit.
- `serviceVisits.records` lists the outcome (`created`, `duplicate`, `conflict`) of up to 100 visits that carried an `externalId`.

A visit **without** an `externalId` that looks like a stored one (same date, odometer, provider and items) is, for a **key**, **never skipped silently**: it is imported and listed in `serviceVisits.possibleDuplicates` (`[{ "row": 1, "visitId": "..." }]`, the stored visit it resembles), so the dry run shows it before you commit. (A browser session without `externalId` keeps skipping such a lookalike and counts it in `duplicates`.)

### 6.8 Receipts

- In a JSON import, receipts travel inside the visit as `attachments`: `{ "fileName", "contentType"?, "sha256"?, "data": "<base64>" }`, up to 10 per visit, 10 MiB each. The type is decided from the bytes (PDF, JPEG or PNG); a declared `contentType` that disagrees is `422 attachment_type`, a wrong `sha256` is `422 attachment_checksum`, an oversize file `422 attachment_too_large`, more than ten `422 attachment_limit`. Identical files inside one visit are stored once.
- Receipts need the same `service.create` as the visit.
- To add a receipt to an existing visit instead, use [`POST .../attachments`](#5-endpoint-reference); a key cannot attach a file the visit already holds (`409 attachment_duplicate`).

### 6.9 Attribution

A committed import is recorded in the key's [activity](#35-activity-history) in the same transaction as the records: a `vehicle.import` summary plus, per kind, `fill_up.import`, `service_visit.import`, `service_attachment.import` and `maintenance_task.import` rows carrying the ids of every created record. If recording fails the import rolls back.

### 6.10 Maintenance tasks in imports

Tasks are imported before the visits that reference them, so `taskRef` links resolve. An identical task already on the vehicle is reused (counted in `maintenanceTasks.duplicates`) and still satisfies `taskRef`. A `taskRef` that matches no task in the file is a validation error. Tasks and service visits are imported even when the instance's Service module is off for a **session**; a **key** gets `404 module_disabled`.

## 7. Idempotency-Key

Network failures leave a client unsure whether a create happened. Send an `Idempotency-Key` header with a create and retry freely: the server writes at most once.

```sh
curl --fail-with-body -X POST "https://your-host/v1/vehicles/${VEHICLE_ID}/fill-ups" \
  -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: ${IDEMPOTENCY_KEY}" \
  -d @fill-up.json
```

### 7.1 Where it applies

| Endpoint | Notes |
| --- | --- |
| `POST /v1/vehicles` | |
| `POST /v1/vehicles/{vehicleId}/fill-ups` | |
| `POST /v1/vehicles/{vehicleId}/service-visits` | |
| `POST /v1/vehicles/{vehicleId}/service-visits/{visitId}/attachments` | |
| `POST /v1/vehicles/{vehicleId}/maintenance-tasks` | |
| `POST /v1/vehicles/{vehicleId}/import` | Commits only; a dry run ignores it |
| `POST /v1/vehicle-imports` | Commits only; a dry run ignores it |

Other writes (`PATCH`, `PUT`, `DELETE`, snoozes, preset apply) are not covered; they are safe to repeat or fail visibly. The header is **optional**, and **only API keys use it**: a session does not even read it.

### 7.2 The header

A client-chosen value of 1 to 255 printable ASCII characters without spaces (`!` to `~`), sent once. A UUID is a good choice. Anything else is `422 validation_failed`. Use a **new value for every distinct operation**, and the same value when retrying the same operation. Only a SHA-256 of the value is stored, so it never reveals a secret by accident; still, do not put secrets in it.

### 7.3 Semantics

- **Same key, same request** (same endpoint, same target vehicle, same payload): the first outcome is returned again, with the original status code and the header `Idempotent-Replayed: true`. Nothing is written twice, **even when the retries arrive at the same moment**: concurrent duplicates are serialised and exactly one write happens.
- **Same key, different request** (different payload, vehicle or endpoint): `409 idempotency_conflict`. It is never a replay.
- If the first request is still being processed when the retry arrives and cannot be replayed yet, the answer is `409 idempotency_conflict` ("still being processed"); retry shortly.
- **Only successes are remembered.** A request that fails (validation, conflict, scope) rolled back and may be retried with the same key, for example after fixing the cause.
- **A replay still passes every check** of the original request: the key must be active, the vehicle in scope, the grants held, the role and module gates satisfied. Otherwise it fails like any other request; a revoked key can never replay an outcome.
- **Replay after deletion.** A replay returns the *original response* even if the created record was deleted in the meantime; nothing is recreated. (In the rare case of a very large stored response the server re-reads the created record instead, and if that is gone the retry fails rather than recreating it.)
- For an import commit, the replayed report is the first report (a very large report is shrunk to its counters).
- **Retention:** 48 hours from the first request. Records vanish with the key, are never part of backups, and an expired record is as good as none (the value can be reused).

## 8. Errors

Every non-2xx response is an RFC 9457 problem (`Content-Type: application/problem+json`):

```json
{
  "type": "about:blank",
  "title": "Insufficient scope",
  "status": 403,
  "code": "insufficient_scope",
  "detail": "This API key does not allow this operation. Required: service.delete.",
  "required": "service.delete"
}
```

| Member | Meaning |
| --- | --- |
| `type` | Always `about:blank` |
| `title` | Short summary; stable per `code` |
| `status` | The HTTP status |
| `code` | **Machine-readable error code. Branch on this.** |
| `detail` | Human-readable explanation; may change, never parse it |
| extras | Some problems add members: `required` and `missing` (insufficient scope), `attachmentId` (`attachment_duplicate`), `visitId` (`external_id_conflict` on a visit write), `report` (`import_invalid`) |

Headers: `WWW-Authenticate: Bearer error="invalid_token"` on `401 invalid_api_key`; `Retry-After` on `429`; `X-Request-Id` on every API-key response. Error text never contains a token, and `5xx` details are not exposed.

An unknown path is `404 not_found`; a known path with the wrong method is `405 method_not_allowed`.

## 9. Rate limits

| Limit | Default | Applies to |
| --- | --- | --- |
| Failed bearer authentication | 20 per minute per client address | Requests whose key is malformed, unknown, expired or revoked. From the 21st failure in a window the answer is `429 rate_limited` instead of `401`. A **valid** key is never blocked by this counter, so one client behind a shared proxy address cannot lock everyone out. |
| Requests per key | 300 per minute | Every ordinary key request |
| Heavy requests per key | 30 per minute | Uploads (any route that takes a raw body: receipts and vehicle photos), exports, imports and dry runs, and new-vehicle imports. These count only against this stricter bucket. |

- Windows are fixed, one minute long. A request over the limit is `429 rate_limited` with a `Retry-After` header: the number of seconds until the window ends. Wait that long.
- "Client address" is the connecting address, or, behind a [trusted proxy](#112-operator-and-proxy-notes), the address the proxy reports.
- Browser sessions are not subject to these limits (sign-in endpoints have their own protections).
- Good behaviour: honour `Retry-After`, add jitter, send creates with an [`Idempotency-Key`](#7-idempotency-key) so retries are safe, and prefer one import over thousands of single creates.

## 10. Worked example: least-privilege service-history import

Goal: import one service visit, with its receipt, into **one** vehicle, using a key that can do nothing else: it can read that vehicle's details and read and write its service history (no delete, no fuel, no other vehicle, no other module), and it expires after seven days. We create the key, prove who it is, look before we leap with a dry run, commit once, verify, and revoke the key.

Requirements: `bash`, `curl` (7.76 or newer for `--fail-with-body`), `jq`, `base64` and `sha256sum`, and an instance on which the **Service** module is switched on (*Administration, Modules*). Run the blocks in order in **one shell**: they share variables. Nothing below contains a real secret; the key is read into a variable by the shell and never typed or echoed.

### Step 0: settings

```sh
export DL='https://your-host'              # your instance, HTTPS
export EMAIL='you@example.com'             # your DriveLoom account
```

### Step 1: sign in once, to mint the key

Keys are created in a signed-in session (a key can never create a key). Signing in also satisfies the "recent sign-in" rule for creating a key. If the account has an authenticator, `login` answers `"state": "mfa_required"`; complete it with `POST /v1/auth/mfa/totp` first. (You can equally create the key in the app under *Account and security, API keys* and skip to step 3.)

```sh
read -rs -p 'DriveLoom password: ' DL_PASSWORD; echo
CSRF=$(curl -sS --fail-with-body -c jar.txt -X POST "$DL/v1/auth/login" \
  -H 'Content-Type: application/json' \
  -d "$(jq -n --arg e "$EMAIL" --arg p "$DL_PASSWORD" '{email:$e,password:$p}')" | jq -r .csrf_token)
unset DL_PASSWORD
```

Find the vehicle id (from the session; or `GET /v1/vehicles` with any key that has `vehicle_info.read`):

```sh
curl -sS --fail-with-body -b jar.txt "$DL/v1/vehicles" | jq -r '.items[] | "\(.id)  \(.name // .model)"'
export VEHICLE_ID='<paste the id of the vehicle>'
```

### Step 2: create the key (7 days, one vehicle, two permissions)

```sh
KEY_JSON=$(curl -sS --fail-with-body -b jar.txt -X POST "$DL/v1/auth/api-keys" \
  -H "X-CSRF-Token: $CSRF" -H 'Content-Type: application/json' \
  -d "$(jq -n --arg v "$VEHICLE_ID" '{
        name: "Service import (one-off)",
        expiresIn: "7d",
        vehicleMode: "selected",
        vehicleIds: [$v],
        permissions: { vehicle_info: "read", service: "read_write" }
      }')")
export DRIVELOOM_API_KEY=$(jq -r .token <<<"$KEY_JSON")   # shown only now; keep it in this variable
export KEY_ID=$(jq -r .id <<<"$KEY_JSON")
unset KEY_JSON
jq -n --arg id "$KEY_ID" '{created_key: $id}'
```

The key appears nowhere on the command line and in no file. In real use, store it in your secret manager instead of a shell variable, and give the job that needs it only that.

To keep the key out of the process list on a shared machine, you can pass the header through a config file on stdin instead of `-H`. The rest of this example uses plain `-H` for readability:

```sh
printf 'header = "Authorization: Bearer %s"\n' "$DRIVELOOM_API_KEY" | curl -sS -K - "$DL/v1/me"
```

### Step 3: who am I?

```sh
curl -sS --fail-with-body -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" "$DL/v1/me" | jq .
```

```json
{
  "user": { "id": "...", "displayName": "..." },
  "authMethod": "api_key",
  "apiKey": {
    "id": "...", "name": "Service import (one-off)",
    "permissions": { "vehicle_info": "read", "service": "read_write" },
    "vehicleMode": "selected", "vehicleIds": ["<your vehicle id>"], "vehicleCreate": false,
    "expiresAt": "<seven days from now>"
  }
}
```

### Step 4: look at the vehicle and its history

```sh
curl -sS --fail-with-body -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" "$DL/v1/vehicles" | jq '.items | map({id, name, odometerUnit, currency})'
curl -sS --fail-with-body -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" "$DL/v1/vehicles/${VEHICLE_ID}" | jq '{id, name, odometerUnit, currency}'
curl -sS --fail-with-body -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" "$DL/v1/vehicles/${VEHICLE_ID}/service-visits?limit=5" | jq '.items | map({servicedOn, provider, externalId})'
```

Only the one vehicle is listed. Any other vehicle id is `404 vehicle_not_found`, and anything outside `vehicle_info` and `service` is refused:

```sh
curl -sS -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" "$DL/v1/vehicles/${VEHICLE_ID}/fill-ups" | jq -c '{status, code, required}'
# {"status":403,"code":"insufficient_scope","required":"fuel.read"}
```

### Step 5: build the import and dry-run it

The import file is a `driveloom.vehicle` JSON document containing one service visit with the receipt embedded. `vehicle` is required but ignored for an existing vehicle, and `fillUps` is `[]` because this key may not write fuel. The `externalId` is the visit's id in the source system: it makes a repeated import skip the visit instead of duplicating it.

For a runnable demonstration, make a tiny placeholder receipt; in real use point `RECEIPT` at your real PDF, JPEG or PNG:

```sh
RECEIPT=invoice-0314.pdf
printf '%%PDF-1.4\n1 0 obj<</Type/Catalog>>endobj\ntrailer<</Root 1 0 R>>\n%%%%EOF\n' > "$RECEIPT"   # demo file only

jq -n --rawfile data <(base64 -w0 "$RECEIPT") --arg sha "$(sha256sum "$RECEIPT" | cut -d' ' -f1)" --arg name "$RECEIPT" '{
  format: "json",
  dryRun: true,
  data: {
    format: "driveloom.vehicle", version: 1, vehicle: {}, fillUps: [],
    serviceVisits: [{
      servicedOn: "2026-03-14",
      odometer: { value: "84210", unit: "km" },
      provider: "Corner Garage",
      totalCost: "189.90",
      externalId: "garage-2026-0314-001",
      items: [
        { name: "Oil and filter change", category: "scheduled", cost: "119.90" },
        { name: "Cabin air filter",      category: "scheduled", cost: "70.00" }
      ],
      attachments: [{ fileName: $name, contentType: "application/pdf", sha256: $sha, data: ($data | rtrimstr("\n")) }]
    }]
  }
}' > import-dry-run.json
```

(`base64 -w0` is GNU; on macOS use `base64 -i "$RECEIPT"`. Adjust `contentType` to `image/jpeg` or `image/png` for those files.)

Send it. It writes nothing:

```sh
curl -sS --fail-with-body -X POST "$DL/v1/vehicles/${VEHICLE_ID}/import" \
  -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" -H 'Content-Type: application/json' \
  --data-binary @import-dry-run.json | tee dry-run-report.json | jq '{dryRun, committed, serviceVisits, errors, previewToken, previewExpiresAt}'
```

```json
{
  "dryRun": true,
  "committed": false,
  "serviceVisits": {
    "total": 1, "created": 1, "duplicates": 0, "invalid": 0,
    "records": [ { "row": 1, "externalId": "garage-2026-0314-001", "outcome": "created", "visitId": "..." } ]
  },
  "errors": [],
  "previewToken": "dlp_...",
  "previewExpiresAt": "2026-11-27T16:55:35.096Z"
}
```

Read it: one visit would be created, nothing is invalid, and `possibleDuplicates` is absent. (Had the visit looked like a stored one but carried no `externalId`, it would be listed under `serviceVisits.possibleDuplicates`; had its `externalId` already existed with different content, it would be a conflict and there would be no token.) Because nothing is invalid, the dry run returned a `previewToken`, valid for 15 minutes and usable once.

### Step 6: commit with the preview token and an Idempotency-Key

The commit must carry **the identical `format` and `data`**: the easiest way to guarantee that is to derive the commit file from the dry-run file, changing only `dryRun` and adding the token.

```sh
PREVIEW_TOKEN=$(jq -r .previewToken dry-run-report.json)
jq --arg t "$PREVIEW_TOKEN" '.dryRun = false | .previewToken = $t' import-dry-run.json > import-commit.json

IDEMPOTENCY_KEY=$(cat /proc/sys/kernel/random/uuid 2>/dev/null || uuidgen)   # one value per intended import
curl -sS --fail-with-body -X POST "$DL/v1/vehicles/${VEHICLE_ID}/import" \
  -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: ${IDEMPOTENCY_KEY}" \
  --data-binary @import-commit.json | jq '{dryRun, committed, serviceVisits}'
```

```json
{
  "dryRun": false,
  "committed": true,
  "serviceVisits": { "total": 1, "created": 1, "duplicates": 0, "invalid": 0, "records": [ { "row": 1, "externalId": "garage-2026-0314-001", "outcome": "created", "visitId": "018f3b1e-..." } ] }
}
```

If the network failed and you do not know whether it went through, send **the same command again with the same `Idempotency-Key`**: you get the first report back with the response header `Idempotent-Replayed: true`, and nothing is imported twice. Sending it with a *new* key but the old token fails (`409 preview_mismatch`: the token was used); run a new dry run, which now reports the visit as a `duplicate` because of its `externalId`.

### Step 7: verify

```sh
curl -sS --fail-with-body -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" \
  "$DL/v1/vehicles/${VEHICLE_ID}/service-visits?limit=5" \
  | jq '.items[0] | {id, servicedOn, provider, externalId, totalCost, currency, items: [.items[] | {name, cost}], attachments}'

VISIT_ID=$(curl -sS -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" "$DL/v1/vehicles/${VEHICLE_ID}/service-visits?limit=1" | jq -r '.items[0].id')
ATTACHMENT_ID=$(curl -sS -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" "$DL/v1/vehicles/${VEHICLE_ID}/service-visits/${VISIT_ID}" | jq -r '.attachments[0].id')
curl -sS --fail-with-body -o downloaded-receipt -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" \
  "$DL/v1/vehicles/${VEHICLE_ID}/service-visits/${VISIT_ID}/attachments/${ATTACHMENT_ID}"
cmp downloaded-receipt "$RECEIPT" && echo "receipt round-trips byte for byte"
```

You, the owner, can also see what the key did: the app's key screen, or `GET /v1/auth/api-keys/{id}/activity` in the session, lists `service_visit.import` and `service_attachment.import` with the new record ids and the request id.

### Step 8: revoke the key and clean up

The job is done; do not leave the key lying around. A key cannot revoke itself, so use the signed-in session from step 1 (or the app):

```sh
curl -sS --fail-with-body -b jar.txt -X DELETE "$DL/v1/auth/api-keys/${KEY_ID}" -H "X-CSRF-Token: $CSRF"   # 204: revoked at once
curl -sS -H "Authorization: Bearer ${DRIVELOOM_API_KEY}" "$DL/v1/me" | jq -c '{status, code}'
# {"status":401,"code":"invalid_api_key"}

curl -sS --fail-with-body -b jar.txt -X POST "$DL/v1/auth/logout" -H "X-CSRF-Token: $CSRF"
unset DRIVELOOM_API_KEY KEY_ID CSRF PREVIEW_TOKEN IDEMPOTENCY_KEY
rm -f jar.txt import-dry-run.json import-commit.json dry-run-report.json downloaded-receipt
```

The revoked key stays in the list as `revoked` (its activity history intact) until you remove it with a second `DELETE`.

## 11. Security guidance

### 11.1 For key holders

- **Least privilege.** Give a key the smallest set of modules, the lowest level and the fewest vehicles that does the job. Prefer `selected` vehicles. Treat `all_current_future` as a deliberate, broad grant, and `full` (which allows deleting) and `never` expiry as exceptions you can justify.
- **One key per integration.** A key per script or device makes revocation and the activity history meaningful.
- **Short expiry for temporary jobs** (`24h`, `7d`), and revoke them when finished. Remove keys you no longer use.
- **Keep keys secret.** Never paste one into a chat, note, ticket, e-mail or source file; never commit it (keep `.env` files out of version control); never put it in a URL or a log. Store it in a password manager, secret store or CI secret, and read it from an environment variable. On shared machines pass it to `curl` with `-K -` as shown in the worked example so it does not show in the process list. Do not embed a key in browser or mobile code: the API sends no CORS headers, keys belong in server-side or local tools.
- **Always HTTPS** to a remote instance. The server refuses keys over plain HTTP from another machine.
- **Rotate on suspicion.** If a key may have leaked, rotate it (the old token dies at once) or revoke it; then review its activity (`GET /v1/auth/api-keys/{id}/activity`). For a wider incident use *revoke all*.
- **Handle errors without leaking.** Log the problem `code` and `X-Request-Id`, not request headers. Never print a token, even in debug output.
- **Retry sensibly:** honour `Retry-After`, use `Idempotency-Key` on creates, treat `401 invalid_api_key` as "stop and tell a human" rather than retrying.
- **Idempotency keys and preview tokens are not credentials**, but do not reuse the one value for different operations.

### 11.2 Operator and proxy notes

For whoever runs the instance (see also [`deploy/proxy`](deploy/proxy/) for Caddy and nginx examples):

- **Terminate TLS at the reverse proxy** and set `DRIVELOOM_PUBLIC_ORIGIN` to the exact URL people use. API keys are accepted only over HTTPS: the app trusts that the request was HTTPS when the connection is TLS, when the request comes from the local machine, or when the **direct peer is listed in `DRIVELOOM_TRUSTED_PROXIES` and its `X-Forwarded-Proto` ends in `https`**. Otherwise keys get `403 https_required`.
- **`DRIVELOOM_TRUSTED_PROXIES`** takes a comma-separated list of proxy IPs or CIDRs, for example `172.16.0.0/12`. Put the address your proxy connects *from* in it, as the app sees it. Without it the app ignores `X-Forwarded-For` and `X-Forwarded-Proto`: keys fail with `https_required` from remote clients, and the failed-authentication rate limit sees every client as the proxy. A proxy on the same host that is **not** listed looks like the local machine, and the app then accepts keys from it over plain HTTP, so list it.
- **Overwrite, never append, `X-Forwarded-For` and `X-Forwarded-Proto`** at the proxy (nginx: `proxy_set_header X-Forwarded-For $remote_addr; proxy_set_header X-Forwarded-Proto $scheme;`; Caddy does this by default), so a client cannot forge them.
- **Pass `Authorization` through unchanged** so API clients reach the app. nginx and Caddy do by default; do not clear it.
- **Strip any `Authorization` header your proxy or SSO gateway adds itself** (Basic auth, `oauth2-proxy`, Cloudflare Access Bearer). The app treats *any* `Authorization` header that reaches it as an API-key attempt and never falls back to the login cookie, so a gateway-injected header turns the whole web app into `401 invalid_api_key`. nginx: `proxy_set_header Authorization "";` Caddy: `request_header -Authorization`. If you protect the site with the proxy's own basic auth, API clients cannot use that hostname; expose a separate hostname or path for them.
- **Do not log `Authorization` headers** in proxy or load-balancer access logs. The app's own failure log contains only the method, the path without its query string and the error, and anything token-shaped in it is replaced; the `Authorization` header is never read for logging.
- **Body size limits.** Imports with embedded receipts can be large (the server accepts up to 96 MiB). The example proxy configurations allow 40 MB, which is the limit you will actually hit; raise it if you import many receipts at once, or split the import.
- **Kill switches.** *Administration, API keys* blocks all keys instantly without deleting them; each user can *revoke all* their keys; disabling an account, account recovery, an operator password reset and restoring a backup also end keys (see [3.4](#34-when-keys-are-revoked-and-when-they-are-kept)).
- **Backups and snapshots.** Built-in backups never contain API keys and a restore clears every key (people create new ones). A **raw database snapshot** (`pg_dump`, a volume or disk copy) does contain key **hashes** (never tokens, but still credentials material), their grants and the preview and idempotency tables. Before you share, expose or restore it somewhere else, delete or invalidate the rows of `api_keys` (for example `DELETE FROM api_keys;` on the copy; permissions, vehicle bindings, idempotency records and previews are removed with them).
- **Audit.** Writes made with a key are attributed in the administrators' audit log (`GET /v1/admin/audit`, `details.apiKey` with the key id and the name at the time) and in the owner's per-key activity. Administrators can see that a key acted, never the token.
- **Upgrading from a version before API keys:** keys are on by default. If anything in front of the app injects an `Authorization` header, fix that first (see above).
